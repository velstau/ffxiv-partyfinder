# 設計ノート（ff_partyfinder）

このドキュメントは「なぜこの形になっているか」を残すためのもの。
何ができるかは [README](../README.md) を参照。

---

## 1. このアプリが解いている問題

FF14 の固定パーティ募集は、ロードストーンの日記機能で行われている。
ところが日記検索は**全文検索しかできない**ため、実際に探すときに困ることがある。

| やりたいこと | ロードストーンでは | このアプリ |
|---|---|---|
| 「絶妖星乱舞の、D3枠が空いている募集」を探す | 全文検索で絞るしかない | 募集ロールで絞り込み |
| どのコンテンツの募集が何件あるか把握する | 一覧を目で数える | コンテンツ別に集計 |
| 「P3から」など進行度で選ぶ | できない | フェーズを解析して表示 |
| 条件を変えて何度も見る | 毎回入力し直す | URLがそのまま条件、検索条件の保存 |

本質的な仕事は **「人が自由に書いたタイトルから、構造化された条件を取り出す」** こと。

## 2. 全体の流れ

```
ブラウザ
   │  GET /?search=1&q=...&keywords=...&role_filter[]=D3
   ▼
PartyFinderController
   │  ① resolveConditions()  … GETパラメータを検証して検索条件に正規化
   ▼
LodestoneBlogService::search()
   │  ② buildUrl()    … ロードストーンの検索URLを組み立てる
   │  ③ fetchPages()  … 5件並列でHTMLを取得（5分キャッシュ）
   │  ④ parsePage()   … DOMXPath でエントリを抽出
   ▼
RecruitAnalyzer::annotate()
   │  ⑤ analyze()     … タイトルとタグから中身を読み取る
   │     └─ config/ff14.php の語彙を使う
   ▼
PartyFinderController
   │  ⑥ prepareEntries()  … 「固定のみ」「募集ロール」で絞り込み
   │  ⑦ sortEntries()     … 並び替え
   │  ⑧ summarize() / groupByContent()  … 集計とグルーピング
   ▼
view('partyfinder.index')   または   StreamedResponse（CSV）
```

依存は **Controller → Service → config** の一方向。
`RecruitAnalyzer` は HTTP もロードストーンも知らず、文字列を受け取って構造を返すだけ。
そのため実際の日記タイトルを並べた回帰テストが書ける。

## 4. 設計判断とその理由

### 4.1 語彙をコードではなく設定に置く

コンテンツ名もロール表記も、パッチのたびに増える。
解析ロジックに埋め込むと追従のたびにコードを触ることになるので、
**`config/ff14.php` だけ直せば済む**形にしてある。

```php
// config/ff14.php
'contents' => [
    ['key' => 'kefka', 'label' => '絶妖星乱舞', 'category' => '絶',
     'patterns' => ['絶妖星乱舞', '絶妖精乱舞', '絶ケフカ']],
    ...
],
```

`patterns` に表記ゆれ（誤字の「絶妖精乱舞」を含む）を並べておけば拾える。
辞書に無いコンテンツは `RecruitAnalyzer::matchContentGeneric()` の汎用ルール
（`◯◯零式` / `極◯◯` / `幻◯◯` / `◯◯激闘戦`）で拾い、それでも分からなければ「その他・不明」に入る。

### 4.2 読み取れなかったものは推測で埋めない

解析できなかった項目は `null` にして、画面では「—」と表示する。

募集条件を誤って埋めると、**実際には募集していない枠に応募してしまう**。
「分からない」と正直に出すほうが、それらしい値を作るより役に立つ。

### 4.3 長い表記から照合する

ロール語彙は照合前に**表記の長い順へ並べ替える**（`RecruitAnalyzer::__construct()`）。

「ピュアヒーラー」を「ヒーラー」より先に試さないと、
「ピュア」が余って正しく読み取れない。同じ理由でコンテンツ辞書の `patterns` も長い順に書く。

また **1文字の略称（暗・学・竜 など）は語彙に入れていない**。
本文中の別の語に当たって誤爆するため。

### 4.4 タイトルだけで判定し、本文は既定で読まない

判定材料はタイトルとタグだけ。本文を読むと1件につき1リクエスト増え、
50件×20ページなら数百リクエストになる。

実際の募集日記はタイトルに条件を詰め込む書き方が主流なので、これで実用になる。
本文からのフェーズ判定は**任意のオプション**として用意してあり、
その場合も上限（`MAX_BODY_FETCH = 60`）を設けて暴走を防いでいる。

### 4.5 本文からフェーズを読むときの誤爆対策

本文には募集条件以外の文章も大量に含まれる。そのまま拾うと、
次のような行をフェーズ表記と誤認する。

| 本文の行 | 誤認しやすい理由 |
|---|---|
| `P1,2,3リリドP4,P5ぬけまる` | 処理法の羅列。P番号が並ぶ |
| `・P2 カーターライズ スキップしません` | ギミック解説 |
| `✒T1：暗黒騎士 Mike Tester(p3～)` | 現メンバーの進捗であって募集フェーズではない |
| `9月中旬開始` | 「〇〇から」の形だが時期の話 |

`RecruitAnalyzer::recruitmentLines()` で募集条件らしい行だけに絞り、
さらに `NOT_A_PHASE`（月・日・時・週・次第・以降…）で時期の言い回しを除外している。
**タイトルにフェーズが書いてあれば本文は見ない**（`phase_source` で出典を記録する）。

### 4.6 表記ゆれの正規化

照合の前に `RecruitAnalyzer::normalize()` で次を揃える。

- 全角英数（`Ｄ３` → `D3`）
- 半角カナ（`ﾒﾝﾊﾞｰ` → `メンバー`）
- 波ダッシュ（`〜` `～` の統一）

正規化しないと「Ｄ３」と「D3」が別物として扱われ、取りこぼす。

### 4.7 取得したHTMLをキャッシュする

ロードストーンは公開サイトであって API ではない。
短時間に何度も叩かないよう、取得HTMLを5分キャッシュし、並列度も5に抑えている。

本文は一覧より変わりやすい（進捗が追記される）が、
同じ記事を何度も取りに行かないよう30分は使い回す。

## 5. 解析の流れ（`RecruitAnalyzer::analyze()`）

タイトル1本から次を読み取る。すべて独立した private メソッドになっている。

```
normalize()            表記ゆれを揃える
   ├─ extractContent()      コンテンツ（辞書 → 汎用ルール の順）
   ├─ extractStyle()        固定 / 野良 / 消化 など
   ├─ extractPhase()        P3 / フェーズ2 / 1-4層 / 最初から / アポカリから
   ├─ extractRoles()        MT ST PH BH H1 D1〜D4 近接 レンジ キャス ジョブ名
   │    ├─ isStandaloneRole()   「D2以外」「H3構成」を除外
   │    └─ sortRoles()          表示順を固定
   └─ extractOpenSlots()    @4 / ＠２名 / 募集 1名（「済1名」は数えない）
```

### 「募集していないロール」の扱い

`D2以外` `暗黒騎士抜き` のような表記は、`ROLE_EXCLUDE_SUFFIX`（以外・抜き・不可・NG）で
検出して `excluded_roles` に分け、画面では**取り消し線**で表示する。
これを募集ロールに混ぜると、募集していない枠が候補に出てしまう。

## 6. ファイル間の連動仕様

| 直す場所 | 連動して確認すべき場所 | 壊れ方 |
|---|---|---|
| `config/ff14.php` の `contents` | `category_order` | 新しいカテゴリを足すと**表の並び順から漏れる** |
| `config/ff14.php` の `roles` | `role_filters[].matches` | 新しいロール表記が**絞り込みに引っかからない** |
| `config/ff14.php` の `role_filters` | `role_group_order` | グループ名が未定義だと**表示順が崩れる** |
| `RecruitAnalyzer::analyze()` の返り値キー | `index.blade.php` / `PartyFinderController::export()` | CSVの列と画面表示が食い違う |
| `LodestoneBlogService::parseBlock()` の XPath | ロードストーン側のHTML構造 | サイト改修で**静かに0件になる** |
| `LodestoneBlogService` の返り値 | `tests/Fixtures/*.html` | フィクスチャが古いと**テストだけ通って実物で壊れる** |

### ロードストーンのHTML構造への依存

`parseBlock()` は `entry__blog_block__*` というクラス名に依存している。
サイトが改修されると抽出できなくなるが、**エラーにはならず0件になる**のが厄介な点。

検索結果の総件数（`parseTotalHits()`）も取得しているので、
「総件数はあるのにエントリが0件」なら構造変化を疑える。

---

## 7. テストの方針

ネットワークに依存しない。ロードストーンへのHTTPは `tests/Fixtures/` の実HTMLを
`Http::fake()` で差し替える。

| テスト | 何を守っているか |
|---|---|
| `tests/Feature/RecruitAnalyzerTest.php` | 実際の日記タイトルを使った解析の回帰（コンテンツ・フェーズ・ロール・空き枠） |
| `tests/Feature/PartyFinderPageTest.php` | 画面とCSVの結合テスト |

### フィクスチャについて

`tests/Fixtures/lodestone_blog_page.html` は実際の検索結果から構造を取ったものだが、
**第三者のキャラクター名・ロードストーンID・アバター画像URLはすべて架空の値に置換してある**
（`Alpha Tester` / `10000001` / `example.invalid`）。
公開情報とはいえ、他人の氏名をリポジトリに再掲載しないため。

募集タイトル自体は解析の対象そのものなので、個人を特定しない形で残している。

## 8. 既知の制約

- **ロードストーンのページャは最大20ページ**（1ページ50件）。それ以上は取得できない。
- **判定材料はタイトルとタグだけ**（本文読み取りは任意・低速）。
  タイトルに条件を書かない募集は「不明」になる。
- **ロードストーンのHTML構造に依存**している。サイト改修時は
  `LodestoneBlogService::parseBlock()` の XPath を見直す必要がある。
- **取得したHTMLは5分キャッシュ**するので、最新状態を強制的に取り直すには
  5分待つか `php artisan cache:clear` を実行する。
